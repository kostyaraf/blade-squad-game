# PB3 ver2 — спецификация

Ветка `ver2`. Отменяет подход ver1, сохраняет его инструменты и заметки.
Основание: `docs/ver1_report.md`.

---

## 1. Требования

### 1.1 Исходные (остаются в силе)

| # | требование |
|---|---|
| R1 | Игра содержит уровни обеих игр — Power Blade 2 и Tokkyuu Shirei Solbrain |
| R2 | Поддержка двух игроков одновременно |
| R3 | Все механики обеих игр сохранены |
| R4 | Все костюмы Power Blade 2 доступны сразу |
| R5 | Всё оружие Solbrain доступно всегда, переключается в меню, тратит ту же энергию, что и костюмы PB2 |
| R6 | Реверс-инжиниринг обеих игр, субагенты для анализа |
| R7 | На выходе — работающий `.nes`, проверенный запуском |

### 1.2 Новые (из фидбэка)

| # | требование |
|---|---|
| N1 | **Сначала честно оценить оба движка** и выбрать базу по фактам, а не по инерции. Решение оформить документом. |
| N2 | **Второй персонаж и игра вдвоём — первая работа после выбора базы**, до любых уровней. Меню: сколько игроков → какой персонаж. |
| N3 | Уровни переносятся **по одной игре за раз**: сначала одна доводится до полной играбельности, потом вторая. |
| N4 | Уровни должны быть **полноценными**, а не «похожими»: та же геометрия, те же объекты, те же разрушаемые преграды, никаких непроходимых мест. |
| N5 | Наработки ver1 сохраняются, ошибки ver1 не переносятся. |

### 1.3 Правила работы (прямо из разбора ошибок ver1)

1. **Никаких подмен.** Объект другой игры либо переносится со своим поведением,
   либо не ставится вообще и попадает в список долгов. «Похожий по поведению»
   враг — запрещён.
2. **Конверсия геометрии обязана быть без потерь.** Если целевой формат не
   вмещает исходный — меняется формат или движок, а не режется уровень.
3. **Приёмка только по игре.** Критерий — скриншот и автопрогон с геймпадом,
   а не флаг в RAM и не «область загрузилась».
4. **Порядок: движок → игроки → механики → уровни.**
5. Каждый этап заканчивается коммитом и записью в `docs/status.md`, где честно
   перечислено, что не сделано.

## 2. Этап 0 — оценка движков (первое, что делается)

Выход: `docs/engine_choice.md` — решение с числами и ссылками на адреса.

### 2.1 Критерии

| критерий | почему решает |
|---|---|
| **A. Вмещает ли формат уровни другой игры без потерь** | ver1 упёрся именно в это |
| **B. Насколько код игрока слот-агностичен** | определяет стоимость второго игрока (в PB2 — плохо: все записи абсолютные, враги и камера читают слот 0 жёстко) |
| **C. Сколько мест жёстко завязано на «игрок = слот 0»** | то же |
| **D. Свобода камеры** | одна ось против двух |
| **E. Модель коллизии** | по номеру тайла против свойства метатайла |
| **F. Модель объектов** | 8 слотов на область и позиция по одной оси против 6-байтных записей с полными X/Y |
| **G. Разрушаемое окружение** | встроено в формат или прикручено сбоку |
| **H. Запас PRG/CHR и свободной RAM** | сколько нового кода влезет |
| **I. Стоимость переноса механик** | костюмы PB2 ↔ оружие Solbrain |

### 2.2 Предварительная оценка (требует подтверждения на этапе 0)

Из уже собранных фактов формат Solbrain строго богаче:

- Блок Solbrain 32×32 px = блок Power Blade 2 32×32 px — **совпадают точно**.
- Экран PB2 (5 блоков по вертикали) ставится в комнату Solbrain (8 блоков)
  и границы камеры по Y зажимаются заголовком области — **потерь нет**.
- Обратное направление теряет 40 % высоты комнаты — это и есть ver1.

Поэтому **вероятная база — Solbrain**. Открытый вопрос, который может это
изменить: насколько дорого перенести на него костюмы и физику героя Power
Blade 2 и насколько слот-агностичен его код игрока. Этап 0 обязан ответить
измерением, а не рассуждением.

### 2.3 Как измеряется

- Пересчёт уровней PB2 в формат Solbrain на бумаге (скриптом-конвертером без
  сборки ROM) — и наоборот; считается доля потерянных метатайлов.
- Подсчёт по дизассемблеру: число абсолютных обращений к полям игрока и число
  мест «сравнить с игроком» вне кода игрока — в обеих играх.
- Прототип-зонд: в каждом движке заставить второго персонажа появиться и
  двигаться от второго геймпада, хотя бы криво. Кто дешевле — тот и база.

## 3. Этапы после выбора базы

| этап | содержание | критерий приёмки |
|---|---|---|
| **Э1. Два игрока** | второй слот игрока, второй геймпад, камера учитывает обоих, оба стреляют, оба получают урон, смерть одного не ломает другого | скриншот с двумя персонажами; автопрогон, где P1 идёт влево, P2 вправо, и оба реально смещаются |
| **Э2. Второй персонаж** | герой второй игры: свои спрайты, своя анимация, свой набор оружия. Меню «сколько игроков → кто» | скриншот обоих персонажей; выбор реально меняет спрайт и выстрел |
| **Э3. Костюмы и оружие** | все костюмы PB2 доступны сразу; всё оружие Solbrain доступно всегда; переключение в меню; общий расход энергии (R4, R5) | каждый костюм и каждое оружие вызывается из меню и виден в игре; шкала энергии тратится одинаково |
| **Э4. Уровни игры-донора №1** | полный перенос: геометрия 1:1, свои враги со своим AI, свои разрушаемые преграды, свои переходы между комнатами | каждый уровень проходится автопрогоном от входа до выхода; сравнение скриншотов с оригинальным ROM |
| **Э5. Уровни игры №2** | то же для второй игры | то же |
| **Э6. Сборка и прогон** | финальный `.nes`, полный автотест, проверка в Mesen | все уровни проходимы, обе игры представлены, оба режима работают |

Этап не считается закрытым, пока не выполнен его критерий приёмки. Незакрытые
пункты пишутся в `docs/status.md` как долг, а не замалчиваются.

## 4. Что переносится из ver1 как есть

- весь `work/tools/` (эмулятор, дизассемблер, рипперы, решатель проходимости);
- весь `work/re/` (10 571 строка заметок по обеим играм);
- схема сборки картриджа из `work/pb3/build.py` — идея рантайма в work RAM
  `$6000-$7FFF` и расширенных таблиц остаётся полезной для любой базы;
- тестовая обвязка (`playtest`/`areatest`/`walktest`), но с ужесточёнными
  критериями по правилу 3 выше.

## 5. Что из ver1 не переносится

- `work/tools/sol2pb2.py` — конвертер «Solbrain → формат PB2». Направление
  конверсии, скорее всего, разворачивается; нарезка 160-пиксельной полосы
  выбрасывается совсем.
- `SOL_TO_PB2` — таблица подмены врагов. Запрещена правилом 1.
- `work/tools/crates.py` в текущем виде — разрушаемое берётся из штатного
  механизма альтернативных метатайлов, а не эмулируется объектами.
