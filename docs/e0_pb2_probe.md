# Э0, зонд: второй игрок в движке Power Blade 2

Измерение 3 из `docs/ver2_spec.md` §2.3 для стороны Power Blade 2.
Сборка: `work/pb3/e0_probe_pb2.py` -> `work/build/probe_pb2.nes`.
Симметричный зонд для Solbrain делается отдельно.

## Результат: **работает**

Два персонажа на экране, каждый ходит от своего геймпада, каждый со своей
анимацией. Скриншот: `docs/e0/pb2_2p_1560.png` (P1 держит влево, P2 вправо).

Замеры на кадре 1560 (стадия 1, оба стоят на одной платформе):

| ввод | P1 x | P1 спрайт | P2 x | P2 спрайт | спрайтов в OAM |
|---|---|---|---|---|---|
| нет | 224 | 11 (стоит) | 200 | 11 (стоит) | 18 |
| `2LEFT` | 224 | 11 | **144** | 07 (идёт) | 14 |
| `LEFT,2RIGHT` | **173** | 07 | **234** | 11 | 14 |

P1 реагирует только на первый геймпад, P2 — только на второй. Ни один не
двигается от чужого ввода.

## Что понадобилось

Всего три изменения в стоковом ROM, 127 байт нового кода:

1. Банк 8, `$8000`: `JMP $8E15` (единственный вызов процедуры игрока за кадр)
   заменён на `JMP $8D6A`.
2. Банк 8, `$8D6A`-`$8DE8` — 150 байт настоящего филлера `$FF` внутри той же
   пары банков 8/9, где живёт игрок, поэтому переключать банки не нужно:
   ```
   JSR $8E15      ; игрок 1, как было
   JSR INIT       ; если слот игрока 2 пуст -- скопировать в него игрока 1
   JSR SWAP       ; обменять слот 0 и слот игрока 2 + обменять геймпады
   JSR $8E15      ; та же процедура, но данные теперь игрока 2
   JSR SWAP       ; вернуть обратно
   RTS
   ```
   `SWAP` обменивает все 29 полей массива объектов. Таблица адресов не нужна:
   базы полей — это `$0400 + n*$16`, n = 0..28, то есть арифметика.
   Обмен геймпадов — `$48<->$49` (нажато) и `$4A<->$4B` (удерживается).

## Две находки, которые стоили времени

**Слот игрока 2 должен быть меньше 6.** Композитор спрайтов (банк 6, `$808F`:
`CPX #$06 / BCC $809F`) берёт указатель на метаспрайт из разных таблиц:
`$8148`/`$81B4` для слотов 0-5 и `$8C88`/`$8D83` для 6-21. Игрок 2 в слоте 21
рисуется, но по таблице врагов — на экране появляется чужая мелкая графика
(было видно в OAM: 4 спрайта вместо 9). В слоте 5 он рисуется правильно.
Цена: игрок 1 теряет один из пяти слотов под выстрелы.

**Игрока 2 нельзя ставить справа от игрока 1.** Камера следует только за
слотом 0, поэтому игрок 2, поставленный на +24 px, оказывается у правого края
экрана, а запрос к геометрии (`$C8A0`) для позиции за пределами загруженных
колонок возвращает `$80` = "твёрдо". Игрок 2 при этом честно отрабатывает всю
свою логику, доходит до `$AD3B BMI $AD84` и получает "уперся в стену", то есть
стоит на месте. Смещение на -24 px решает вопрос — но это и есть первое
доказательство того, что камера остаётся однопользовательской.

## Что зонд НЕ делает

Это измерение стоимости, а не реализация. Не сделано:

| | почему это важно |
|---|---|
| камера следует только за игроком 1 | игрок 2 не может уйти за край экрана — это главный оставшийся кусок работы, и он требует переписать модель камеры (`b14 $D3B8` считает цель скролла из голых `$0508`/`$04C6` и `$0116`) |
| враги не видят игрока 2 | десятки мест по всем банкам сравниваются с голым слотом 0 (`work/re/pb2_two_players.md` §6) |
| слот 5 не зарезервирован | процедура выдачи слотов под выстрелы 1..5 не найдена (числится в неизвестных в §"Risks"), поэтому серия выстрелов может затереть игрока 2 |
| блок `$0110-$013F` не обменивается | в этом тесте движению не помешал, но там лежат счётчики игрока; свободной RAM под теневую копию в Power Blade 2 нет — единственный свободный кусок `$0669-$067F` это 23 байта, а нужно 48 |
| костюм, энергия, жизни — общие глобальные | по `work/re/pb2_suits.md` это переменные на сейв, а не на игрока |
| смерть и респавн не проверялись | есть подозрение (§Risks), что смерть игрока 1 через `sub_D746` чистит все слоты |

## Оценка

Появление и независимое управление вторым персонажем в Power Blade 2 —
**дёшево**: 127 байт и три патча. Всё остальное — **дорого**: камера, реакция
врагов и место под состояние второго игрока требуют правки модели движка, а не
точечных патчей. Числа для сравнения с Solbrain — в `docs/engine_choice.md`.

## Побочная находка, важная для всех прошлых измерений

Эмулятор разбирает кнопки в строке ввода **по запятым** (`nesemu.c`,
`load_input`, `strtok(p, ",")`). `work/tools/mkinput.py` собирал их через
пробел, то есть строка `1500 RIGHT A` — это один неизвестный токен, и нажатий
не происходило вовсе. Все автотесты ver1, где игрок должен был прыгать или
стрелять (`walktest.py`, проверки разрушаемых ящиков), на самом деле шли без
кнопок A и B. `mkinput.py` исправлен. Вывод ver1 "выстрел ни разу не попадает
по ящику" получен на этом сломанном вводе и **не доказан**.
