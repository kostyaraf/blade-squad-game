-- destructible background, PB2 -> Solbrain --

PB2 marks a broken block with one of the 8 bits of $3B, per area, and the
hitbox is object type $0C ($8A5D).  Solbrain switches a metatile ID, not a
map cell ($D101/$0540), so keeping PB2's per-instance behaviour costs one
private metatile ID per breakable.
st  type-$0C records  max/area  extra metatile IDs needed (worst area)
----------------------------------------------------------------------
 0                 4         2                              2
 1                 5         2                              2
 2                 0         0                              0
 3                 8         4                              4
 4                 1         1                              1
 5                 5         4                              4
 6                 0         0                              0

PB2 record = 4 bytes: position ALONG the scroll axis in 16-px units,
type, position ACROSS the axis in pixels, flags ($E4BD).  Solbrain record
= 6 bytes with full 16-bit X and Y ($AE7C), so it holds a PB2 record with
room to spare.  Objects live 12 at a time in Solbrain ($CE1D) against 8 in
PB2 ($E4B1), and Solbrain has 64 'alive' flags per stage ($0560).

====================================================================================================
THE SPECIFIC QUESTIONS FROM 2.2 / 2.3
====================================================================================================

1) block size: PB2 block = 32x32 px = 4x4 tiles, 16 bytes ($DBDE);
   Solbrain block = 32x32 px = 2x2 metatiles, 4 bytes ($D0D6).
   SAME PIXEL SIZE.  PB2 stores the 16 tiles flat, Solbrain stores them
   through a metatile indirection -- a repack, not a loss.

2) does a PB2 horizontal screen (5 blocks = 160 px) fit a Solbrain room
   (8 blocks = 256 px)?  Yes: 5 <= 8, 3 block rows of padding.
   Camera Y is clamped by area-header bytes 7/8, which are HIGH BYTES
   only ($E73A/$E73F, $3C/$3E are forced to 0), so the clamp is in whole
   256-px steps: the padding is visible unless it is authored as scenery.
   PB2 shows 176 scanlines of playfield ($AE=1 -> IRQ latch $AF);
   Solbrain shows 224.  NOT a data loss.

3) PB2 vertical areas: a screen holds 8 blocks (256 px) of data but only
   240 px are ever drawn ($EAA5).  240 is not a multiple of 32, so the
   32-px block grid of consecutive vertical screens is offset by 16 px.
   16 px alignment (the metatile grid) is preserved, so re-packing into
   Solbrain blocks costs new block records, not geometry.

4) longest PB2 area found: 6 screens (format cap is 16, $DFB4 masks $66
   with #$0F).  The Solbrain room grid is 16 wide, so a 6-screen
   horizontal area fits one room row.

5) the reverse cap: a Solbrain room chain of R rooms is R*256 px.  A PB2
   horizontal area covers at most 16*256 = 4096 px, a PB2 vertical area
   at most 16*240 = 3840 px, so a vertical chain of more than 15 rooms
   cannot be expressed at all.
