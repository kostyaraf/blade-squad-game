# Нова на объектах Solbrain: аудит кода, 2026-10-03

Исполнитель `nova-sol`, вспомогательный анализ только чтением. Godot и
playthrough не запускались. Ни один уровень и ни одно взаимодействие этим
документом не принимаются: ниже проверенные связи кода, прежние доказательства
и цели для обычных прохождений. Новых NSB без воспроизведения не присваивалось.

Нова — `heroes:[0]`: `Pb3Pair.PB2 = 0`, Solbrain — `SOL = 1`.
`Pb3List.records()` даёт Solbrain входы `63 + stage`, коды `s0.0…s19.0`.

## Два конкретных риска реализации, ещё без живого воспроизведения

1. **Лифт не передаёт Нове динамический пол.** `SolAsPb2.class_byte/terrain_at`
   читают только `SolLevel.collision_at`; полей `map_kind`, `$75`, `$72` нет.
   `_supply_surfaces` в `Pb3Pair` вызывается только для PB2. Поэтому родная
   линия лифта может двигаться, а Нова — падать или упираться в статическую
   карту. В `script.json` реальные dispatcher-комнаты s1/s2 с `$AA46`:
   `$53,$63,$73,$83,$93,$A3,$B3,$C3,$D3`; их босс `$A9C6` — `$43`.
   У s13 финальная `$A89A` содержит `$A8AF` (включение несущей карты),
   `$A94B` в `$15` её останавливает. Номер комнаты означает столбец в младшей
   тетраде и строку в старшей; это положение камеры, не точка телепорта.
   Сначала добраться обычным вводом, затем фиксировать расхождение опоры.

2. **Исправление стартового пикселя отсутствует при переходе.**
   `Pb3List.enter()` корректирует Нову `spot.y -= 1`, если исходная точка
   лежит на поверхности. `Pb3Session._travel()` кладёт `two.home()` напрямую.
   Значит, холодный вход может работать, а переход в тот же уровень —
   поставить Нову внутри пола. Проверять первый RIGHT после каждого
   перехода, без прыжка, прежде всего s0→s8 и s9→s18. Причину подтверждать
   коллизией пола в новой точке; воздушный вход корректировать нельзя.

## Что не считать подтверждением

- Прежние численные результаты тестов в документах — история, не повторная
  проверка текущей ветки.
- `verify_pb3_floor.py` проверяет статическую геометрию на искусственно
  выбранных точках; сценарный лифт и полное прохождение он не закрывает.
- Диспетчеры и карты разделяются несколькими s-кодами, но сценарии/начальная
  камера различаются; проход s0 не принимает s8, кроме непрерывной записи
  реального перехода и победы.
- Координаты объектов вне текущих границ камеры и повторённые экраны всего
  4096×4096 массива нельзя считать доступными маршрутами.
- GAP-02/03/05/07/08/10/12/13 остаются решениями объединённого PB3.
  Для Новы на Solbrain нет картриджа со смешанной парой: проверяются родной
  алгоритм Новы, алгоритм объекта Solbrain и их адаптер отдельно.

## Уточнение лифта: разрывы до адаптера

Первый источник — `work/re/sol_fixed.asm`, `$FBDB LDA $7D` → `$FBDD STA $70`:
запрошенный сценарным кодом режим становится текущим на границе NES-кадра.
`SolScript.run/pack/unpack` такой границы не реализует. Его LINK `$70` читается
из `view.map_kind` и возвращается туда же; сценарий пишет `$7D`, который
остаётся только в тени. Единственная найденная реализация `z70 = z7d` —
`SolFlow`, используемая отдельной концовкой, не живой PB3-сессией.

Второй разрыв — камера PB3. `Pb3Pair._drive_view` вычисляет `sol_pending`
из позиции героя; `SolTurn.slid_already` отключает родной `SolCamera.step`.
Режим `$3C` требует именно `_down`: `y -= fall`, с учётом `hold` и нижней
границы. Простая публикация `$70` ещё не запускает автоматическую езду.

Минимальный контракт интеграции при воспроизведённом дефекте:

1. На установленной по NES границе кадра принять `$7D` в `$70`; не менять
   `map_kind` преждевременно внутри `$A8AF`.
2. Передать режим, `view.fall`, `pool.z75`, `pool.z72`, `pool.cam_y` и
   `hold`; езду камеры применять по родному `$F24B`, а её шаг одновременно
   передавать `slid` и `SolAsPb2.cam_y`.
3. Для Новы добавить динамическую опору в адаптер/контроллер, сохранив родной
   смысл `$D035`: линия `(z75 << 4) + cam_y`, твёрдая зона только на
   0…255 шестнадцатых ниже линии, поправка `vy - penetration + z72`.
   В координатах Новы стопа на один пиксель выше поверхности; это требуется
   учесть при посадке, а не сделать линию постоянной твёрдой стеной.
4. В этом режиме статические стены/потолок не действуют у родного Solbrain
   (`$D014/$A26E`). Как применять это к Нове, фиксировать отдельно, если
   требуется новое правило PB3; родная карта должна обеспечивать маршрут.

Три наблюдения — кодовые риски, не воспроизведённые NSB. Родной тест
`verify_sol_script.py` сеет память NES перед каждой подпрограммой и потому
не обнаруживает отсутствующую между кадрами публикацию `$7D→$70` в сессии.

## s19: штатный запуск и завершение последнего боя

Холодный вход s19 — камера `$22`, сценарий `$9DF9`, таблица `9E0A` с шагом
`$58`. Здесь два объекта в начале не означают два HP-бара босса:

- `$A05B` ставит type `$11` в slot0 (mind `$6F`, HP80), type `$12` в slot11
  (mind `$72`, HP64) по x=`$3700`, y=`$2A00` шестнадцатых, то есть `(880,672)`.
- Шаг1 `$A091` ждёт high-byte x героя `>= $2C`, то есть world x `>=704`.
  Если до него не дошли, атаки не запускают бой. ROM сам пишет RIGHT, но
  актуальный живой PB3 не передаёт весь scripted pad Нове; обычный RIGHT
  позволяет выполнить это условие вручную без изменения состояния.
- Шаг2 `$A0A6` двигает камеру вправо до high-byte `$31 == $2A` (x=672).
- Шаг3 `$A0BF` ждёт, пока mind slot0 перестанет быть `$2F`. Gate `$915B`
  ждёт `z58==3` и конца своей анимации; затем сам удаляет slot11 и превращает
  slot0 в mind `$30`. Хвост убивать не требуется.
- Бой `$923B` принимает гостевые атаки через `SolObjects.arms_hit`: значение
  контакта картинки должно иметь ненулевые младшие шесть бит, без `$20/$80`,
  а между снятиями HP требуется `cool>=9`. Картинки меняются по фазам боя.
- Когда HP достигает0, `$8850` ставит mind|`$80`; шаг4 `$A0D0` замечает это,
  затем `$9E84` сам задаёт kind `$0F` — начало родной смерти. `_done` не
  должен устанавливать `$0F` для всех врагов.
- Дальше `$9E9C` ждёт kind>=`$11` и запускает цепочку концовки. Переход
  `mode=$4C` происходит только в самом конце `$9FF4`, после fade.

Для зависания отчёт должен называть `$58`, kind/mind/life/cool slot0 и
положение камеры. «Оба HP0, ничего не происходит» без номера стадии не
разделяет незапущенный бой, штатное ожидание анимации и дефект сценария.

Первоисточники: `work/re/sol_pair8.asm`, участок `$9DF9…$A0D8` (в листинге
часть размечена как байтовые данные); `work/re/sol_pair2.asm` `$915B/$923B`;
`work/re/sol_pair8.asm` `$8850`; `game/data/sol/script.json` таблица `9E0A`;
`game/data/sol/objects.json` templates `$11/$12`.
